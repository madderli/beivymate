帮助手册

技能需要把您的工作经验转化为清晰、可执行的要求。本手册帮助您说明工作目标、所需资料、处理步骤和结果标准，减少遗漏和歧义，让技能更准确地按您的方法工作。

工作目标

编写要点

  • 范围具体、目标明确；避免“智能处理所有问题”等宽泛表述。
  • 适用场景也应在文件头部的 description 中说明，便于发现技能。

应写内容

  • 做什么： 一句话能力，用这个技能完成哪项具体工作。
  • 什么情况下用： 用熟悉的语言描述使用场景，例如：客户给了一份需求文档时。
  • 不用于什么： 说明不属于这个技能的工作内容，避免范围过大，建议至少写一条。例如：输入是源代码、缺陷单、会议纪要时不使用。

注意事项

  • 合格标准： 换个人，不需要猜，也能判断这个技能是否适用于当前工作。
  • 反例： “一款强大的需求分析工具”——没说干什么、什么时候用，不能用于什么，等于广告。

输入

编写要点

  • 输入可以是文字、文件、数据、工具读取的内容等，不必限定为文档。另外，需要说明缺失、无效或矛盾输入如何处理。

应写内容

  • 技能执行前需要的信息、资料、参数及前提条件；哪些必需、哪些可选；必要的格式和有效性要求。

注意事项

  • 区分每次执行提供的资料与长期参考的资料（例如规范、术语表），说明各自用途和必要性；长期参考资料可在正文中引用或放入 references/，引用时标明来源。具体附件、路径和前序结果在调用时提供，不在通用技能里绑定。参考资料是否阻塞取决于它对当前工作的必要性。
  • 合格标准： 缺少后无法开展工作的资料才列为必需；“有更好”的列为非必需，写清缺失影响及建议处理方式。实际调用前统一汇总缺项：必需资料须补齐才能执行，非必需资料由用户统一决定，不逐项弹窗。
  • 反例： 只写“需要一份文档”，没有说明文档需要包含什么。仅在确有必要时限定格式，不必填写实际来源。

工作步骤

编写要点

  • 指令应可执行。顺序必须严格时写清楚；允许多种方法时保留判断空间。必要时说明中间检查和失败后的处理方式。

应写内容

  • 从接收输入到形成结果的有顺序的操作方法，包含：判断条件和分支；需要使用的工具、脚本或参考文件。
  • 处理动作： 每一步要完成什么。
  • 使用依据： 需要使用哪些输入或前面形成的结果。
  • 完成标准： 做到什么程度才算完成，尽量让其他人也能判断。
  • 中间结果（按需）： 本步形成什么，供哪些后续处理使用。
  • 异常处理（按需）： 不能达到完成标准时，如何说明和请求处理。

注意事项

  • 执行规则： 每步围绕一个清晰目标展开。无法达到继续工作必需的完成标准时，说明原因并请求处理，不带着无依据的假设继续。后续步骤可组合原始资料和前面形成的结果，不限于紧邻上一步。技能内部步骤不自动成为独立工作流节点。
  • 第一类反例： “认真分析文档”、“深入理解需求”——没有动作也没有标准；
  • 第二类反例： “分析并输出清单”——如果分析方法和清单要求都没有说明，执行者无法判断怎样才算完成。必要时拆步，不机械要求每个动词独占一步。

输出

编写要点

  • 根据输出后的用途，来约定文档可以是自然语言建议，也可以是严格的 JSON、代码或文件。需要固定格式时应明确，允许灵活表达时也应说明。不强制绑定具体交付文件或模板。

应写内容

  • 最终应返回或生成什么，以及内容、结构、格式和交付方式。
  • 每个产出都要写三样： 1.名称；2.内容（见下面说明）；3.格式。格式要具体，有必要时说明章节、表格结构或表达方式，例如：表格几列、文档分几节。或者依据工作本身要求的专业格式限制，例如：测试报告模板等专业模板。
  • 分析类结果应区分事实（有资料依据）、判断（推断及依据）与待确认事项（疑点与不确定性），可用章节、表格列或备注表达，不强制固定三节，也不要求代码或翻译等产物采用分析报告结构。

注意事项

  • 合格标准： 客户拿到输出，直接使用，不用再问“这份东西长什么样、哪部分是确定的、哪部分还得确认”。
  • 反例： “输出一份报告” —— 不知道要出什么内容要求、什么格式的报告。

边界｜约束｜处理

编写要点

  • 写明何时可以继续、何时需要询问、何时必须停止；不能让模型自行补造关键事实或声称完成未执行的操作。
  • 边界： 整个技能不接什么活，至少一条，比如不写测试用例、不执行测试、不判断业务本身对不对。这是 agent 首先的范围，要一眼看清。
  • 约束： 接了活之后做事必须遵守的规矩，分依据类、格式类、禁止类写，比如每个结论必须有原文依据、不猜、不脑补、不改原文。
  • 处理： 遇到无法判断、资料不足、资料矛盾时怎么办，要选清楚。建议写成：记为待确认，不擅自选边；不冲突的部分继续做，核心资料缺失时停下来请客户补充，不要自行编造。

应写内容

  • 不适用范围、禁止行为、必须遵守的规则、权限或环境限制，以及异常、歧义和无法完成时的处理方式。

注意事项

  • 必须遵守什么： 业务规则、资料依据、保密要求等。
  • 禁止做什么： 例如编造规则、擅自修改原文、超出授权范围。
  • 资料矛盾怎么办： 列明双方依据和影响，不擅自选边。
  • 无法判断怎么办： 区分可以记录为输出疑点的情况，以及无法继续、必须请求人工处理的情况。
  • 处理范围： 明确哪些内容不应扩展处理，避免重复其他章节。
  • 反例： 把所有规矩都塞进边界里，边界越列越长，反而看不清范围；也别在这里重复工作目标里的“不用于”，边界只在一处写全。

验收要求

编写要点

  • 尽量可观察、可验证，例如字段齐全、引用可追溯、测试通过；避免只有“质量高”、“分析深入”等主观描述。
  • 每条都要能由另一个人照着判断，比如：输入输出要求清晰且满足必要格式约束、每步都有判定标准、边界已声明、事实和判断和待确认没有混在一起、没有编造缺失信息、没有留着“……”没填。
  • 验收要写检查方法，不只是写目标。例如：写“每条结论都能找到依据或被标为待确认”。

应写内容

  • 判断结果是否正确、完整、符合要求的检查条件，以及适用的验证方法。

注意事项

  • 合格标准： 照着这张单子逐条打勾，全过才能交付；有一条过不了，回去改对应的章节，不要只改验收这一节。
  • 应覆盖哪些范围，不能遗漏什么。
  • 内容需要达到什么准确性、完整性和可追溯性。
  • 哪些要求能够逐条检查。
  • 是否明确说明资料缺失、未覆盖范围和不确定性
  • 反例： “质量高”、“分析深入”、“结果要准确”—— 描述过于主观，没有验证标准和方法。

示例（可选）

编写要点

  • 示例应与指令一致，重点展示难以用文字说明的格式或判断方式。示例数量按需，不替代规则，也不等于实际验证。
  • 建议提供示例输入或场景及期望结果，按需补充反例和原因。期望结果应符合输出要求，不强制分三节；有不确定性的案例更能展示边界。
  • 示例最好用真实输入，不要编一个什么都不缺的完美例子；最好带一个有待确认项的例子，正好示范缺资料时怎么处理。

应写内容

  • 典型输入、期望输出，以及必要的边界案例或错误示例。

注意事项

  • 示例可选： 没有附带示例不意味着没有做过测试；附带示例也不等于真实运行已验证。示例无需提供真实客户资料，可以使用虚构且明确标注的场景。没有示例不影响技能发布；有示例也不代表已经通过实际运行验证，所以，建议至少自己私下跑一例验证过再发布，哪怕不把示例贴进模板里。
